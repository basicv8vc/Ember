## 1. Executive Summary

In PR `#190` (M1-D8), local `workerd` telemetry measured **`56.6–61.15` (`~57–61`) DO SQLite `rowsWritten` per event** across the durable turn paths (`51.0` on the 3-RPC fast path). Under ADR-0006's cost model (`68.4M` events/month at `100k MAU`, `$1.00 / 1M` DO rows written above `50M` included), DO SQLite writes account for **`77–84%` of total Cloud Runtime spend** above `1k MAU`, pushing Cloud Runtime over ADR-0006 budgets:

- **`10k MAU`:** `$412.53–$440.92/mo` vs `$300/mo` target (**exceeds by `$113–$141/mo`**)
- **`100k MAU`:** `$4,602.85–$5,303.26/mo` vs `$3,500/mo` target (**exceeds by `$1,103–$1,803/mo`**)

### Headline Findings

1. **Index maintenance is the #1 write amplifier (`25–26` writes/event, `~42–44%` of all DO SQLite writes):**
   - `AgentHeadDO` executes **`21` index B-tree writes/event** on durable turns (including a **100% duplicate index** `idx_messages_conv_seq` on `conversation_messages`, a non-partial `UNIQUE` index on `assistant_turns.response_message_id` that indexes `NULL` on insert, a redundant `idx_v2_outbox_budget_sync_op_rev` already enforced by `outbox_id PRIMARY KEY`, and `4` hidden `sqlite_autoindex_*_1` writes on `TEXT`/composite-PK tables lacking `WITHOUT ROWID`).
2. **Alarm bookkeeping & spurious post-commit Alarm #2 waste `7–10` writes/event:**
   - `AlarmMultiplexer.syncPlatformAlarm` persists `armed_alarm_at_ms` into `v2_recovery_coverage` in SQLite (`3.8–4.75` `UPDATE`s/event) even though Cloudflare DO provides `storage.getAlarm()` at **zero SQLite write cost** (already used by `GlobalBudgetDO`).
   - `AlarmMultiplexer.runAlarmCycle` unconditionally runs `UPDATE v2_recovery_coverage SET alarm_fail_count = 0` on every alarm fire (`1.1–1.75` no-op writes/event when `alarm_fail_count` is already `0`).
   - `commitTurn` arms the DO alarm for `budget_sync` (`next_attempt_at_ms = nowMs`) _before_ `relayBudgetSync` synchronously relays and ACKs it, triggering a **spurious Alarm #2** (`0.60–0.75` extra fires/turn) and premature D1 coverage retirement/re-registration churn (`+3.5–4.0` DO writes + `+3.1` D1 writes on sequential turns).
3. **`GlobalBudgetDO` actual M1 write count is `10` rows/event (`+1` higher than D8's M0 constant `9`):**
   - D8 reused M0's hardcoded `9` rows/event (`4 + 2 + 3`) for `GlobalBudgetDO`. Auditing the actual M1 `GlobalBudgetLedger` DDL and statements yields **`10` rows/event** (`reserveGlobal = 5`, `authorizeGlobalSend = 1`, `settleGlobal = 4`: `5` table writes + `5` index writes), placing true unoptimized M1 totals at **`57.6–62.15` (`~58–62`) rows/event**.
4. **Low-risk optimizations alone (Tier 1 + Tier 2) cut Durable Path writes from `58–62` down to `36` rows/event (`-38%` to `-42%`) and PASS both `10k` and `100k` MAU Cloud Runtime targets:**
   - **Break-even threshold** (at `0.61` D1 writes/event): **`<= 40` DO `rowsWritten/event`** (`$296.25/mo` @ `10k`, `$3,440.05/mo` @ `100k`).
   - **After Tier 1 + Tier 2 (`36` rows/event, `0.61` D1 writes/event):** **`$268.89/mo` @ `10k MAU`** (`-$172.03/mo`, `-39%` vs D8 idle-cycle) and **`$3,166.45/mo` @ `100k MAU`** (`-$2,136.81/mo`, `-40%` vs D8 idle-cycle) — **both comfortably under `$300 / $3,500`**.
   - **After Tier 1 + Tier 2 + Tier 3 (`30` rows/event blended 80/20 Fast/Durable, `0.20` D1 writes/event):** **`$225.67/mo` @ `10k MAU`** and **`$2,700.71/mo` @ `100k MAU`** (`-$2,602.55/mo`, `-49%` vs D8 idle-cycle).

### 2.2 How `workerd` Counts `SqlStorageCursor.rowsWritten`

In Cloudflare Durable Objects SQLite (`tests/integration/support/v2-m1-full-runtime/runtime-worker.ts#L153-L199` sums `cursor.rowsWritten` across every `storage.sql.exec()` call):

- **`INSERT` into a rowid table (default when `WITHOUT ROWID` is omitted):**
  - `1` write for the table B-tree (`OP_Insert`)
  - `+1` write for **each** B-tree index receiving an entry (`OP_IdxInsert`), including:
    - Hidden `sqlite_autoindex_<table>_1` created automatically for `TEXT PRIMARY KEY` or composite `PRIMARY KEY (...)` (only `INTEGER PRIMARY KEY` aliases `rowid` without an autoindex)
    - Hidden `sqlite_autoindex_<table>_N` for every column/table `UNIQUE` constraint (**including `NULL` values** in non-partial `UNIQUE` indexes)
    - Every explicit `CREATE [UNIQUE] INDEX` whose `WHERE` predicate (if partial) matches the inserted row
- **`UPDATE` modifying non-indexed columns only:** `1` write (table B-tree overwrite).
- **`UPDATE` modifying an indexed column where the row enters or remains in the index:** `1` (table) `+ 1` per affected index (`OP_IdxInsert`).
- **`UPDATE` where a row leaves a partial index** (e.g., `status = 'running' -> 'completed'` or `state = 'pending' -> 'acked'/'cancelled'`): `1` (table) `+ 0` (`OP_IdxDelete` is not billed as `rowsWritten`).
- **`UPDATE` matching `0` rows** or **`INSERT ... ON CONFLICT DO NOTHING` on conflict:** `0` writes.

This accounting model reproduces all four D8 measurements (`42.00`, `47.60`, `51.75`, `52.15`) to within `0.00–0.25` rows/event.

## 4. Classification of Write Waste

### 4.1 Duplicate Writes (Same Information Persisted Twice)

1. **Duplicate B-tree index `idx_messages_conv_seq`** ([schema.ts:274](../../packages/runtime-v2/src/agent-head/schema.ts#L274) vs [schema.ts:306](../../packages/runtime-v2/src/agent-head/schema.ts#L306)): Identical `(conversation_id, sequence)` key maintained twice on every user and assistant message (`+2` writes/event).
2. **Redundant `idx_v2_outbox_budget_sync_op_rev`** ([recovery/schema.ts:155-157](../../packages/runtime-v2/src/recovery/schema.ts#L155-L157)): Deterministic `outbox_id = budget_sync:<operationId>:rev:<revision>` already enforces `(operation_id, revision)` uniqueness via the primary key (`+1` write/event).
3. **Dual-write `budget_sync` outbox + `model_attempts` settlement** ([budget.ts:930-980](../../packages/runtime-v2/src/agent-head/budget.ts#L930-L980), [budget.ts:1031-1040](../../packages/runtime-v2/src/agent-head/budget.ts#L1031-L1040), [budget-sync.ts:227](../../packages/runtime-v2/src/recovery/budget-sync.ts#L227)): Every settlement writes all settlement fields to `model_attempts` (`+1`), duplicates the same data as JSON into `v2_dispatch_outbox` (`+4`), and on synchronous relay ACK updates BOTH `model_attempts.global_synced_at_ms` (`+1`) and `v2_dispatch_outbox.state = 'acked'` (`+1`) — `7` writes total for one state transition.
4. **Dual-row `agent_spend_days` (`tenant` + `principal`)** ([budget.ts:233-250](../../packages/runtime-v2/src/agent-head/budget.ts#L233-L250), [budget.ts:844-863](../../packages/runtime-v2/src/agent-head/budget.ts#L844-L863)): Inside a single-tenant `AgentHeadDO`, every reserve and settle updates two separate rows (`tenant` and `principal`, `4` writes/event) even though the tenant total is the sum of its principal row(s) in that DO.
5. **Hidden `rowid` + PK autoindex duplication** on `TEXT`/composite-PK tables (`assistant_turns`, `model_attempts`, `v2_dispatch_outbox`, `global_budget_reservations`, `global_budget_settlements`) lacking `WITHOUT ROWID` (`+6` writes/event).

### 4.2 Ineffective / No-Op `UPDATE`s & Spurious Lifecycle Churn

1. **Unconditional `alarm_fail_count = 0` `UPDATE`** ([registry.ts:994-999](../../packages/runtime-v2/src/recovery/registry.ts#L994-L999)): Fires on every `alarm()` execution even when `alarm_fail_count` is already `0` (`+1.1` to `+1.75` writes/event).
2. **SQLite persistence of `armed_alarm_at_ms`** ([registry.ts:954-960](../../packages/runtime-v2/src/recovery/registry.ts#L954-L960)): Writes to `v2_recovery_coverage` `3.8–4.75` times per durable turn (`2` on fast path) solely to deduplicate `setAlarm()`, whereas `storage.getAlarm()` already provides authoritative alarm state at `0` SQLite write cost.
3. **Indexing `NULL` in `assistant_turns.response_message_id UNIQUE`** ([schema.ts:323](../../packages/runtime-v2/src/agent-head/schema.ts#L323)): Every turn starts with `response_message_id = NULL` by `CHECK` constraint, yet SQLite inserts that `NULL` into the non-partial unique index (`+1` write/event).
4. **Unused `UNIQUE` index on `global_budget_reservations.global_grant_id`** ([global-budget/schema.ts:13](../../packages/runtime-v2/src/global-budget/schema.ts#L13)): Never referenced in any `WHERE` clause (`ownedGrant` looks up by PK `operation_id` and checks `global_grant_id` in JS; `+1` write/event).
5. **Spurious Alarm #2 caused by `syncPlatformAlarm` running before `relayBudgetSync`** ([turn-commit.ts:118-130](../../packages/runtime-v2/src/agent-head/turn-commit.ts#L118-L130)): Arms an immediate alarm for a `budget_sync` row that is ACKed milliseconds later in the same request, causing `0.60–0.75` wasted alarm fires/turn and triggering immediate D1 coverage retire/re-register churn on sequential turns (`+3.5–4.0` DO writes + `+3.1` D1 writes/event).
6. **Redundant second `ackOutboxSync` call** ([outbox.ts:658](../../packages/runtime-v2/src/recovery/outbox.ts#L658) after [recovery-service.ts:1120](../../packages/runtime-v2/src/agent-head/recovery-service.ts#L1120)): Matches `0` rows (`0` `rowsWritten`), but adds an unnecessary `transactionSync` + SQL statement per durable claim.

### 4.3 Safely Mergeable State Updates

1. **Inline best-effort `queue.send()` after `prepareTurn` Stage 3** with `next_attempt_at_ms = commitNow + 5_000` fallback: Eliminates Alarm #1 and the intermediate `pending -> enqueued` (`markPublishSuccessSync`) state transition (`-2` writes on `v2_dispatch_outbox` + `-1` alarm fire), while keeping the durable outbox row + 5s alarm as 100% crash-safe backup.
2. **Delayed D1 coverage retirement (idle TTL hysteresis, e.g., `5–15 min`)**: Prevents `covered -> registering(retire) -> uncovered -> registering(ensure) -> covered` thrashing across back-to-back conversation turns (`-3.5` DO writes and `-3.1` D1 writes on sequential turns).
3. **Unifying `budget_sync` retry queue into `model_attempts`** via a partial index `WHERE global_grant_id IS NOT NULL AND global_synced_at_ms IS NULL AND state != 'reserved'`: Eliminates the separate `v2_dispatch_outbox` `budget_sync` row on normal turns while preserving atomic crash-safe durability.
4. **Inlining `rev = 0` settlement payload on `global_budget_reservations`**: Avoids inserting into `global_budget_settlements` on the 99.9% single-settlement normal path (`-1` write after `WITHOUT ROWID`), retaining full `global_budget_settlements` rows for `rev > 0` or incident-bearing settlements.

## 6. Guardrails — What MUST NOT Be Optimized Away

To uphold _"不削弱持久化、幂等、Fencing 或预算安全机制"_, the following writes are **explicitly irreducible** and must NOT be removed or deferred:

1. **`markAttemptSent` Two-Phase Write (`send_authorizing_at_ms` -> `authorizeGlobalSend` -> `send_started_at_ms`, `2` writes):**
   - Merging or dropping `send_authorizing_at_ms` creates a crash window where `GlobalBudgetDO` authorizes a send, `AgentHeadDO` crashes before writing `send_started_at_ms`, and recovery falsely treats the attempt as `provablyUnsent` (`released` instead of `unknown_billed`), breaking conservative budget safety (ADR-0001 / V2-M0-A §7.3).
2. **Separate `conversations.last_sequence` updates in `prepareTurn` and `commitTurn` (`2` writes):**
   - User messages must receive a durable monotonic sequence before returning `201` ACK; assistant messages arrive after external model execution and may interleave with subsequent user messages.
3. **Durable pre-RPC persistence of `turn` outbox (on durable path) and settlement sync state (on all paths):**
   - External side effects (`Queue.send`, `GlobalBudgetDO.settleGlobal`) must always be backed by an already-committed SQLite record in `transactionSync` so DO crashes never cause silent task loss or unreleased global budget reservations.
4. **`GlobalBudgetDO` synchronous `reserve -> authorize -> settle` state transitions (`6–7` writes after Tier 1–3):**
   - Eliminating `authorizeGlobalSend` or moving global accounting to asynchronous eventual consistency would violate hard global daily spend caps under concurrent agent contention.
5. **Excluding `conversation_messages` from `WITHOUT ROWID`:**
   - SQLite's `WITHOUT ROWID` stores full row payloads inline in the PK B-tree; because `conversation_messages.text` can be up to `8 KiB`, using `WITHOUT ROWID` would severely degrade B-tree fanout and increase page splits/storage amplification.

### Key Cost Takeaways

1. **Both `10k` (`<= $300`) and `100k` (`<= $3,500`) targets are met as soon as DO writes reach `<= 40` rows/event and D1 writes reach `<= 0.61` rows/event.**
2. **Tier 1 + Tier 2 alone is sufficient to pass with a `~10%` safety margin** even under 100% Durable Queue execution (`$268.89` @ `10k`, `$3,166.45` @ `100k`) — without requiring any Tier 3 A/B seam refactor.
3. **Combined Unit Economics Context:** As noted in D8 §14.4, LLM + Sandbox spend (`$32.4k/mo` illustrative or `$3.98k/mo` ZDR+Offload at `10k MAU`; `$324.5k/mo` or `$39.8k/mo` at `100k MAU`) remains `88–99%` of total COGS, so the practical goal is bringing Cloud Runtime cleanly below ADR-0006's `$300 / $3,500` guardrails rather than chasing the theoretical `20`-row assumption at the expense of durability or code complexity.
