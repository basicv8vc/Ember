# Managed PostgreSQL and Cloudflare Hyperdrive PoC

Status: Neon is approved by the CTO as Ember Alpha's PostgreSQL provider. PR #135 records synthetic Neon/Supabase and temporary Hyperdrive comparison evidence. The temporary Cloudflare probes were removed; no paid or production resource is in use. L4-D's credential rotation and claim-concurrency matrix are pending; this PR remains Draft and does not claim 10,000-user capacity.

## Decision

Adopt the CTO direction: cloud-native, pay-as-you-grow, best-of-breed; start at low cost and scale without changing Ember's PostgreSQL business contract. Keep the existing PostgreSQL schema, migrations, tenant rules, API authorization, and lease semantics. Do not move state to D1 or add a database abstraction without need.

**Neon is approved for Ember Alpha.** This selection closes the Alpha provider discussion; it is not a 10,000-user capacity or production-readiness claim. Keep the PostgreSQL schema, migrations, tenant rules, API authorization, and lease semantics unchanged. Supabase remains an alternative if future measured requirements justify reconsideration; AWS RDS/Aurora remains an expansion or resilience reference.

The app-facing database boundary remains PostgreSQL through the existing pg driver and migrations. Supabase Auth/Data API or Neon backend features are optional product capabilities, not reasons to replace Ember's current auth, API, or tenancy contracts. A managed endpoint, secret, and later deployment binding are the provider-specific pieces.

PR #135 records live PostgreSQL 17.11 results for the approved Neon and Supabase Free test projects. A fresh direct Neon connection after owner-password rotation also returned PostgreSQL 17.11, `max_connections=901`, and an encrypted client socket using TLS 1.3. The public schema has 17 applied migration rows and `ember_private.apple_identity_nonce_replays` exists. Both providers accepted the migration set used for the comparison. Neon is the Alpha selection. See PR #135 for exact checksums, Hyperdrive probes, idle recovery, backups, and cost assumptions; do not infer sustained capacity from those short tests.

Both Cloudflare provider guides use PostgreSQL over TLS and recommend a direct database endpoint for Hyperdrive. PR #135 includes account-backed Hyperdrive probes for both providers. Agent C's fresh Workers deployment is separate and remains gated on the rotated owner credential and a least-privilege `ember_worker` Hyperdrive origin.

Provider regions are not interchangeable with Worker execution regions. The tested Neon and Supabase projects were in Singapore; the Neon Hyperdrive probes used Cloudflare's SIN edge. This is a controlled same-region comparison, not a global latency assessment.

## Local code and contract audit

- packages/postgres/src/pool.ts creates a lazy pg.Pool, sets connection/idle/statement timeouts, and routes idle and checked-out socket errors to optional hooks.
- packages/postgres/src/migrator.ts takes a session-level advisory lock while verifying migration history, then applies each migration and checksum row transactionally. Run the migrator directly against PostgreSQL, not through Hyperdrive: Hyperdrive transaction pooling does not support session-level advisory locks. Runtime coordination uses transaction-level pg_advisory_xact_lock, which Hyperdrive documents as supported.
- PR #139's exact HEAD contains 16 migrations; PR #138 adds `0017_apple_nonce_replay.sql`, which does not change the lease tables. The lease queue and original claim test are unchanged between those heads. No schema or business-contract change is part of this PoC.
- Lease claims and reapers rely on FOR UPDATE SKIP LOCKED; B1 identity/session and other coordination paths use transaction-level advisory locks. A live Hyperdrive Worker run still needs to check these behaviors together.
- The existing PostgreSQL integration/chaos/E2E suites cover migration checksum/idempotence, tenant-qualified constraints, durable-task/Unknown ACK replay, duplicate idempotency, lease concurrency, connection termination/recovery, error mapping, and secret-safe diagnostics. These local tests do not prove provider or proxy behavior.
- Ember API remains the authorization and tenant boundary. Keep database credentials, Supabase service-role keys, JWT signing secrets, and any production database access out of iOS configuration. Keep the Ember schema private and unexposed from the Supabase Data API.

It creates 10 temporary schemas and submits 256 synthetic claim attempts in total, without a sustained load phase. The reproduction uses a 5-second statement timeout from the prior probe; the matrix uses the repository default of 10 seconds. Both use the repository's 5-second connection-acquire timeout.

The runner accepts only the direct, unpooled Neon `ember_test_owner` URL for database `ember_test`. Store it in a mode-600 temporary environment file outside the checkout, then invoke:

```sh
node --env-file=/path/to/secure/neon-diagnostic.env --import tsx scripts/neon-claim-diagnostic.ts
```

It creates and drops only the random `ember_it_*` test schemas managed by the existing integration fixture, uses synthetic tasks, and never prints the URL or raw server error text. The JSON report captures pool acquire wait split into queued/new-connection/idle-reuse, `totalCount`/`idleCount`/`waitingCount` peaks, per-SQL client-observed round-trip p50/p95, request p50/p95 and per-request outcomes, PostgreSQL `pg_stat_activity` wait events and sampled active-query age, SQLSTATE/error categories, and lease/task/run/event invariants including tenant references. Query round-trip time includes network latency; sampled active-query age is approximate and neither metric is a server CPU measurement.

## Least-privilege outline

Neon-specific constraint: PR #135 confirmed that the Neon administrative role could create `ember_worker` and apply table grants, but Neon rejected the script's explicit `ALTER ROLE ... NOSUPERUSER` with SQLSTATE `42501`. Do not run the generic role-setup script unchanged on Neon. Create a separate login with only the default non-admin attributes (and `NOINHERIT`), grant only the required database/schema/table access, exclude `schema_migrations`, set a bounded statement timeout, then verify role flags and a password-authenticated connection. PR #135's earlier catalog/grant check passed, but `SET ROLE` was denied and the actual runtime login was not tested; L4-D must complete that login check.

L4-D created `ember_worker` without a password, then applied the PR #138 B1 grants individually because the managed role DDL failed at transaction commit with SQLSTATE `XX000`. Catalog checks show LOGIN and NOINHERIT, with SUPERUSER, CREATEDB, CREATEROLE, REPLICATION, BYPASSRLS, schema CREATE, `tasks` SELECT, and `schema_migrations` SELECT all false. The grants were applied for the PR #138 Conversation tables and nonce replay table; ACL probes confirm Conversation SELECT, nonce INSERT, and denial of task and migration reads. The role's `statement_timeout` and `idle_in_transaction_session_timeout` are both 5 seconds. Neon rejected a SQL-supplied SCRAM verifier with `XX000`; password setup and a password-authenticated login remain pending the Neon console handoff. Do not configure Hyperdrive until that login succeeds.

1. Create separate migration and runtime roles with the target provider's admin console or administrative SQL session. PR #139's provider-neutral smoke uses `ember_migrator`/`ember_runtime`; the Workers API in PR #138 uses `ember_worker`.
2. Run [the PostgreSQL role setup SQL](../../infra/postgres/sql/least-privilege-roles.sql) once while connected to the target database. It uses current_database(), creates the private ember schema owned by the migrator, and sets per-database search paths/timeouts.
3. Set unique passwords through the provider console/secret manager. Give direct migration jobs the migrator URL; configure Hyperdrive with the least-privilege `ember_worker` URL. Never put either password in source, mobile settings, or test output.
4. Run all existing migrations as the migrator over the direct endpoint. Afterward, apply [the runtime grants SQL](../../infra/postgres/sql/least-privilege-runtime-grants.sql) as the migrator; it excludes schema_migrations. Test actual queries under each runtime login.
5. Verify provider-specific database names, default privileges, role permissions, and migration search_path behavior. If a migration fails, record the denied statement and grant only the missing privilege; do not make the Worker role an owner or superuser.
6. If Supabase Data API is enabled, confirm ember is not exposed and no Ember table privileges are granted to anon or authenticated.

The SQL is a starting point, not a hosted verification. Role creation/permissions and the complete migration sequence must pass in each provider's disposable PostgreSQL 17 target before production consideration.

## Backup, pause, and rollback plan

- Before first migration and before each production migration, export a logical backup with pg_dump --format=custom or the provider CLI. Store the export separately from the database with restricted access; record the provider, region, PostgreSQL major, migration checksums, and exact application SHA.
- Verify each export with pg_restore --list. On a schedule, restore it into a separate disposable PostgreSQL 17 database, run readiness and integration checks, and record restore duration and data-loss point.
- Neon Free offers a short instant-restore history (up to six hours or 1 GB of data changes, one snapshot), but that is not an independent backup. Neon paid plans show longer restore windows and optional snapshots/scheduled backups; include their cost in a future approved production model.
- Supabase Free can pause a project after a week of inactivity and has no automated backups. Supabase Pro lists daily backups for seven days; PITR is a paid add-on. Document the owner and resume path and test reconnection after an operator resumes a disposable project.
- Migrations are forward-only. Roll back Worker/API code while keeping additive schema compatible. For destructive data loss, restore to a new project, verify it, then explicitly change the Hyperdrive target; never overwrite the source project during a restore rehearsal.
- Production gate: confirm PostgreSQL 17 on the chosen endpoint, run the provider-specific suites, pass the actual Hyperdrive Worker smoke, time a full logical restore, set accepted RPO/RTO and latency/cost thresholds, and obtain prior approval for any paid resource or plan. No hard $0 production requirement applies.
