# Managed PostgreSQL and Cloudflare Hyperdrive PoC

Status: local compatibility and official-documentation audit only. No provider project, Hyperdrive configuration, production deployment, or paid resource was created. Repository audit based on main at db9fab1, 2026-11-07. Neon and Supabase hosted endpoint tests remain unrun.

## Decision

Adopt the CTO direction: cloud-native, pay-as-you-grow, best-of-breed; start at low cost and scale without changing Ember's PostgreSQL business contract. Keep the existing PostgreSQL schema, migrations, tenant rules, API authorization, and lease semantics. Do not move state to D1 or add a database abstraction without need.

**Neon is the provisional first PoC candidate for the database-only need. Supabase is a valid alternative; AWS RDS/Aurora remains an expansion or resilience reference. No provider is approved for production.** This is a shortlist, not a production decision: actual PostgreSQL version, endpoint reachability, Hyperdrive semantics, restore time, region latency, and workload cost need live validation.

The app-facing database boundary remains PostgreSQL through the existing pg driver and migrations. Supabase Auth/Data API or Neon backend features are optional product capabilities, not reasons to replace Ember's current auth, API, or tenancy contracts. A managed endpoint, secret, and later deployment binding are the provider-specific pieces.

### PostgreSQL version, TLS, and region evidence

Cloudflare's supported-provider table currently labels Neon and Supabase as PostgreSQL 15.x, while Neon documents PostgreSQL 17 availability and Supabase documents major-version upgrades. That documentation conflict does not prove the version of a new or existing endpoint. The shared smoke requires PostgreSQL 17 and records the endpoint's actual server_version_num; run it separately against each disposable provider target before making a provider decision.

Both Cloudflare provider guides use PostgreSQL over TLS and recommend a direct database endpoint for Hyperdrive. Neon Free's direct endpoint and Supabase Free's IPv6-only direct endpoint are different networking cases; only an account-backed Worker run can establish reachability from the intended Hyperdrive configuration. Use TLS certificate validation for the direct smoke URL and record the actual Worker/Hyperdrive path separately.

Provider regions are not interchangeable with Worker execution regions. Select a database region based on user geography and data-location requirements, then measure from the actual Worker. Supabase currently publishes 17 exact AWS regions; Neon's current official latency matrix lists the regions above. Neither endpoint region was provisioned for this audit.

## Local code and contract audit

- packages/postgres/src/pool.ts creates a lazy pg.Pool, sets connection/idle/statement timeouts, and routes idle and checked-out socket errors to optional hooks.
- packages/postgres/src/migrator.ts takes a session-level advisory lock while verifying migration history, then applies each migration and checksum row transactionally. Run the migrator directly against PostgreSQL, not through Hyperdrive: Hyperdrive transaction pooling does not support session-level advisory locks. Runtime coordination uses transaction-level pg_advisory_xact_lock, which Hyperdrive documents as supported.
- The 16 existing migrations use ordinary PostgreSQL tables, constraints, indexes, ON CONFLICT, procedural DO blocks, and FOR UPDATE SKIP LOCKED. They have no CREATE EXTENSION step or explicit public object reference. No schema or business-contract change is part of this PoC.
- Lease claims and reapers rely on FOR UPDATE SKIP LOCKED; B1 identity/session and other coordination paths use transaction-level advisory locks. A live Hyperdrive Worker run still needs to check these behaviors together.
- The existing PostgreSQL integration/chaos/E2E suites cover migration checksum/idempotence, tenant-qualified constraints, durable-task/Unknown ACK replay, duplicate idempotency, lease concurrency, connection termination/recovery, error mapping, and secret-safe diagnostics. These local tests do not prove provider or proxy behavior.
- Ember API remains the authorization and tenant boundary. Keep database credentials, Supabase service-role keys, JWT signing secrets, and any production database access out of iOS configuration. Keep the Ember schema private and unexposed from the Supabase Data API.

## Reproducible checks

### Local PostgreSQL 17

Use a disposable PostgreSQL 17 instance; never point these commands at production data.

```
export TEST_DATABASE_URL='postgresql://ember:...@127.0.0.1:5432/ember_test'
pnpm test:unit
pnpm test:integration
pnpm test:chaos
pnpm test:e2e
```

The repository integration, chaos, and E2E suites create test data and must target a dedicated test database. In this worktree, exact-HEAD local verification against PostgreSQL 17.11/TLS passed: build, typecheck, unit (1,491), integration (546), chaos (30), E2E (55), and the provider-neutral database smoke (16 migrations applied once and skipped on the second run). The least-privilege SQL was also exercised locally: the migrator applied all migrations, the runtime read an application table, and the runtime could not read migration history. These are local-engine results only.

### Separate disposable Neon and Supabase database smoke

Use a new disposable PostgreSQL 17 target for each provider. Use its **direct, unpooled TLS endpoint** and an administrative test role that can create/drop schemas. Do not use production credentials or a runtime-only role for this smoke. The provider variable is a caller-supplied label; the script does not infer or attest the host from that label.

Neon:

```
export CLOUD_POSTGRES_SMOKE_PROVIDER=neon-free
export CLOUD_POSTGRES_SMOKE_DATABASE_URL='postgresql://<role>:<password>@ep-<endpoint>.<region>.aws.neon.tech/neondb?sslmode=verify-full'
pnpm db:smoke:cloud-postgres
unset CLOUD_POSTGRES_SMOKE_DATABASE_URL CLOUD_POSTGRES_SMOKE_PROVIDER
```

Supabase:

```
export CLOUD_POSTGRES_SMOKE_PROVIDER=supabase-free
export CLOUD_POSTGRES_SMOKE_DATABASE_URL='postgresql://<role>:<password>@db.<project-ref>.supabase.co:5432/postgres?sslmode=verify-full'
pnpm db:smoke:cloud-postgres
unset CLOUD_POSTGRES_SMOKE_DATABASE_URL CLOUD_POSTGRES_SMOKE_PROVIDER
```

The smoke refuses anything other than PostgreSQL 17 over TLS. It creates a random ember_cloud_smoke_* schema, applies all 16 migrations, reruns the migrator, checks rollback, unique/idempotent replay, tenant-scoped reads, and competing SKIP LOCKED claims, then drops only that generated schema. It reports provider label, server version, TLS, database size, connection limit, and pass/fail booleans; it never prints the hostname, username, password, connection string, or raw server error. A cleanup failure is a failed smoke and requires manual cleanup of only the generated schema reported by the error.

For each provider, preserve the output with the exact commit SHA, region, endpoint type, PostgreSQL version, and date. Then run the existing integration/chaos/E2E suites against a separate disposable database to validate Ember's full Unknown ACK, retry/reconnect, tenant, and error-code contracts. The direct smoke does not execute these higher-level suites.

## Least-privilege outline

1. Create separate ember_migrator and ember_runtime roles with the target provider's admin console or administrative SQL session.
2. Run [the PostgreSQL role setup SQL](../../infra/postgres/sql/least-privilege-roles.sql) once while connected to the target database. It uses current_database(), creates the private ember schema owned by the migrator, and sets per-database search paths/timeouts.
3. Set unique passwords through the provider console/secret manager. Give the direct migration job the migrator URL; configure Hyperdrive with the runtime URL. Never put either password in source, mobile settings, or test output.
4. Run all existing migrations as ember_migrator over the direct endpoint. Afterward, apply [the runtime grants SQL](../../infra/postgres/sql/least-privilege-runtime-grants.sql) as the migrator; it excludes schema_migrations. Test actual queries under the runtime login.
5. Verify provider-specific database names, default privileges, role permissions, and migration search_path behavior. If a migration fails, record the denied statement and grant only the missing privilege; do not make the Worker role an owner or superuser.
6. If Supabase Data API is enabled, confirm ember is not exposed and no Ember table privileges are granted to anon or authenticated.

The SQL is a starting point, not a hosted verification. Role creation/permissions and the complete migration sequence must pass in each provider's disposable PostgreSQL 17 target before production consideration.

## Backup, pause, and rollback plan

- Before first migration and before each production migration, export a logical backup with pg_dump --format=custom or the provider CLI. Store the export separately from the database with restricted access; record the provider, region, PostgreSQL major, migration checksums, and exact application SHA.
- Verify each export with pg_restore --list. On a schedule, restore it into a separate disposable PostgreSQL 17 database, run readiness and integration checks, and record restore duration and data-loss point.
- Neon Free offers a short instant-restore history (up to six hours or 1 GB of data changes, one snapshot), but that is not an independent backup. Neon paid plans show longer restore windows and optional snapshots/scheduled backups; include their cost in a future approved production model.
- Supabase Free can pause a project after a week of inactivity and has no automated backups. Supabase Pro lists daily backups for seven days; PITR is a paid add-on. Document the owner and resume path and test reconnection after an operator resumes a disposable project.
- Migrations are forward-only. Roll back Worker/API code while keeping additive schema compatible. For destructive data loss, restore to a new project, verify it, then explicitly change the Hyperdrive target; never overwrite the source project during a restore rehearsal.
- Production gate: confirm PostgreSQL 17 on the chosen endpoint, run the provider-specific suites, pass the actual Hyperdrive Worker smoke, time a full logical restore, set accepted RPO/RTO and latency/cost thresholds, and obtain prior approval for any paid resource or plan. No hard $0 production requirement applies.
